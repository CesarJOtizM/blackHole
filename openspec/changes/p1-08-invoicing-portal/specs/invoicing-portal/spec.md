# Invoicing Portal Specification

## Purpose

Customers register their own billing data from a QR or link, without exposing anyone else's data (PRD-M3, TRD-00 8.5, Ley 1581). Cloud-only, for cloud and hybrid sites.

## Requirements

### Requirement: Account-Bound Portal Links

Each pre-bill MUST carry a signed, single-purpose link bound to one account, generated by the operation owner even offline, expiring at invoice issuance or after 24 h. A receipt or invoice link MUST show "in process" while pending and the invoice with PDF once accepted, until the re-invoicing window ends. A link MUST NOT expose other accounts.

#### Scenario: Receipt printed during an outage
- GIVEN a hybrid site offline prints a receipt
- WHEN the customer scans it before and after reconnection
- THEN it shows "in process", then the accepted invoice and PDF

#### Scenario: Expired link
- GIVEN a pre-bill whose invoice was issued
- WHEN the customer opens its link
- THEN data entry is refused and no account data is shown

### Requirement: Masked Acquirer Autocomplete

The system SHALL look up name and email for an ID only under a valid link and MUST show both masked. Lookups MUST be rate-limited per link and IP and MUST yield to invoice issuance in the per-NIT quota.

#### Scenario: Known ID
- GIVEN a valid link
- WHEN the customer types an ID known to the DIAN
- THEN "J*** P***" and "j***@gmail.com" are shown for confirmation

#### Scenario: Lookup unavailable or abused
- GIVEN the provider is down or the link hit its lookup limit
- WHEN an ID is typed
- THEN nothing is revealed and manual entry continues

### Requirement: Validated Data With Consent

The system MUST require ID type, number, person type and name, validate NIT check digit (modulo 11), email and DANE municipality, and MUST NOT store data without Ley 1581 consent recorded with date, policy version and link. Deletion MUST stop future use but keep data backing issued invoices.

#### Scenario: Invalid NIT
- GIVEN a NIT with a wrong check digit
- WHEN submitted
- THEN it is rejected with a field error

#### Scenario: Consent missing
- GIVEN valid data without accepted policy
- WHEN submitted
- THEN nothing is stored

### Requirement: Remembered Data With One-Time Code

On opt-in, data SHALL be stored per company, usable at all its sites and never by another company. It MUST be revealed only after validating a one-time code sent to the holder's registered email or phone.

#### Scenario: Returning customer
- GIVEN remembered data for an ID
- WHEN the customer validates the received code
- THEN the data is offered for confirmation

#### Scenario: Only the ID is known
- GIVEN remembered data for an ID
- WHEN someone types that ID without the code
- THEN no remembered data is shown

### Requirement: Delivery to the Cash Register

Received data MUST mark the account "data received" at the register in real time; if portal and register data differ, the cashier MUST choose before charging. During a hybrid outage data MUST wait in the cloud, and deferred issuance MUST use it only if it arrived first. In cloud mode the register is stopped during an outage.

#### Scenario: Online site
- GIVEN a connected site
- WHEN the customer confirms data
- THEN the account shows "data received"

#### Scenario: Data after consumer-final issuance
- GIVEN an invoice issued to consumer final
- WHEN portal data arrives
- THEN the invoice is not edited and re-invoicing is offered

### Requirement: Re-invoicing

Within the company window (default same day), the system SHALL issue a credit note voiding the consumer-final invoice and, only once accepted, a new invoice with the customer's data, linked and audited. If the company requires approval, an authorized user MUST approve first. Outside the window the provider MUST NOT be called.

#### Scenario: Approved within window
- GIVEN a consumer-final invoice issued today
- WHEN re-invoicing is approved
- THEN the credit note is accepted before the new invoice and two documents are consumed

#### Scenario: Outside window
- GIVEN an invoice older than the window
- WHEN re-invoicing is requested
- THEN it is rejected without contacting the provider
